# 모바일 OTP : TOTP 2단계 인증 (`26-w11-mobile-otp`)

> 실습 안내와 완성 기준은 [`guide.md`](./guide.md), 기획서는 [`PRD.md`](./PRD.md) 참고

## 소개

- 앱 이름 : KEYSPACE
- 컨셉 : Google Authenticator 스타일의 인증기 앱형
- 일반 인증기와 차이점 : 계정을 추가할 때 웹앱이 직접 비밀 키를 발급하고 QR을 보여 줌 → 스마트폰 Authenticator로 스캔해 두 기기의 코드를 비교할 수 있게 구성
- 화면 구성
  - 메인 : 계정 카드 목록 (서비스명, 계정명, `123 456` 형식 6자리 코드, 30초 원형 타이머)
  - 계정 추가 : 우측 하단 + 버튼 → 모달에서 서비스명·계정명 입력 → 비밀 키 발급 → QR과 Base32 비밀 키 표시 → 등록 완료
  - 카드별 기능 : 코드 복사, 코드 검증, 삭제
  - 하단 : localStorage 평문 저장 경고 문구

## 나의 AI 기획·구현 과정

### 선택한 협업 방식

- Gemini 웹에서 기획 → VS Code + GitHub Copilot(Agent)으로 단계별 구현
- 기획 순서
  - 앱 형태, 화면 흐름, 검증 위치, 저장 방식을 먼저 직접 결정
  - 결정한 내용을 Gemini에 전달해 PRD 작성
  - PRD 검토 후 수정 : 설치되지 않은 Tailwind 언급 제거, QR 라벨 encodeURIComponent 인코딩 추가, 검증 입력칸 숫자 6자리 제한 추가
  - 수정한 PRD를 `PRD.md`로 저장소에 커밋
- 구현 순서
  - Copilot에 코드 작성 없이 구현 계획만 먼저 요청
  - 계획 검토 후 localStorage 저장 단계를 앞으로 이동 (뒤에 두면 새로고침할 때마다 웹 계정이 사라져 폰 재등록을 반복해야 했음)
  - totp.js → 계정 추가 모달 → 계정 카드 → localStorage·경고 문구 → 코드 검증 → 복사·삭제 순으로 한 단계씩 구현
  - 단계마다 브라우저·스마트폰으로 직접 확인 후 커밋

### 시행착오

- 시작 전 GitHub 로그인에서 2단계 인증 코드 입력 화면에 막힘 → 인증 앱 코드로 해결, 이번 과제에서 만드는 TOTP를 실제로 먼저 겪은 셈
- Copilot Agent 모드에 PRD 파일만 첨부하고 요청 문장 없이 보냈더니 바로 추론을 시작함 → 정지 후 "코드는 쓰지 말고 계획만" 조건을 붙여 다시 요청
- 브라우저 콘솔에서 totp.js 테스트 코드를 붙여넣자 크롬이 붙여넣기를 차단 → Self-XSS 방지 기능임을 확인하고 `allow pasting` 입력 후 진행
- 스마트폰 코드 비교 시 30초 경계 직전에는 한쪽만 먼저 바뀌어 달라 보일 수 있음 → 새 주기가 시작된 직후 비교
- `npm run lint` 결과 경고 3개 (useEffect 안에서 setState 직접 호출, `set-state-in-effect`), 에러 0개 → 동작에는 영향 없음

## TOTP 원리 및 보안 점검 (사이버보안과 체크포인트)

### TOTP 계산 검증

- `src/utils/totp.js`에 비밀 키 생성, Base32 인코딩·디코딩, 64비트 빅엔디안 카운터, HMAC-SHA1, Dynamic Truncation 구현
- 브라우저 콘솔에서 RFC 6238 공식 테스트 벡터 6개 (59, 1111111109, 1111111111, 1234567890, 2000000000, 20000000000초) 계산 → 6개 모두 PASS

### crypto.getRandomValues()를 쓰는 이유

- `Math.random()`은 암호용이 아닌 의사 난수 → 내부 상태를 알면 다음 값을 예측할 수 있음
- 비밀 키가 예측되면 공격자가 같은 OTP를 계산할 수 있어 2단계 인증 자체가 무력화됨
- `crypto.getRandomValues()`는 OS가 제공하는 암호학적 난수 생성기(CSPRNG) 사용 → 20바이트(160비트) 비밀 키 생성, Base32로 바꾸면 32글자

### 브라우저 안에서 처리하는 이점 (Zero-Transmission)

- 비밀 키 생성과 HMAC-SHA1 연산을 `crypto.subtle`로 브라우저 안에서 처리 → 네트워크로 비밀 키가 나가지 않아 중간 탈취나 서버 로그 유출 위험이 없음
- QR도 외부 QR 생성 API 대신 qrcode.react로 브라우저에서 직접 그림 → 외부 API를 쓰면 QR 안의 비밀 키가 그 서버로 전송됨
- Network 탭 점검 : 필터 All, 목록 비운 뒤 비밀 키 발급 → 요청 0건 확인
- 페이지 로딩 시 보이는 요청은 localhost 앱 파일, Vite 개발 서버 웹소켓, 크롬 확장 프로그램(Adobe) 요청으로 앱의 외부 전송과 무관
- `crypto.subtle`은 보안 연결(HTTPS 또는 localhost)에서만 동작 → 두 배포 사이트 모두 HTTPS라 정상 동작

### localStorage 저장에 대한 판단

- 저장하지 않으면 새로고침마다 계정이 사라지고, 폰에는 옛 계정이 남아 코드가 맞지 않게 됨
- 저장하면 편하지만 비밀 키가 평문으로 남음 → 개발자 도구 Application 탭에서 `mobile-otp-accounts-v1` 값에 비밀 키가 그대로 보이는 것 확인
- 판단 : 편의성을 위해 저장하되 화면 하단에 "비밀 키가 이 브라우저에 저장됩니다. 공용 PC에서는 사용 후 계정을 삭제하세요." 경고 표시
- 저장 데이터가 깨져 있어도 앱이 멈추지 않고 오류를 안내하도록 처리

### 스마트폰 연동 결과

- Google Authenticator로 QR 스캔 → 서비스명·계정명(`@` 포함)이 깨지지 않고 등록됨
- 웹 카드의 6자리 코드와 스마트폰 코드 일치 확인
- 새로고침 후에도 카드가 유지되고 코드가 계속 일치
- 검증 기능 : 폰 코드 입력 시 성공(초록), 000000 입력 시 실패(빨강)
